# Classroom Translator (SIH Prototype)

A classroom translation MVP: a teacher speaks Hindi or English into their
laptop/phone mic, and the system shows the Santali (Ol Chiki) translation
immediately, with spoken Santali audio following — instantly for a set of
common classroom phrases, or generated live (slowly) for anything else.

**Scope of this MVP:** one direction only (teacher → Santali text + audio),
push-to-talk, free-form speech. No offline mode, no other languages, no
student→teacher direction, no auth/database.

## Why two modes (Demo Mode + Live Mode)

Indic Parler-TTS — the only self-hosted TTS model with Santali support (see
"Known limitations" below) — takes **~30-90 seconds per sentence on CPU**.
That's a hard limit of the model's architecture on this hardware, not a
tuning problem (see below). So the app has two modes:

- **Demo Mode**: click any of 53 pre-generated classroom phrases, grouped into
  6 categories with a search box (built once via `scripts/build_phrasebook.py`)
  and its Santali text + audio appear instantly. No microphone needed — good
  for a live SIH demo that can't wait 60+ seconds on stage.
- **Live Mode**: hold the mic button and speak freely. Santali **text**
  appears in ~2-3 seconds (STT + translation, both optimized -- see "Latency"
  below). Santali **audio** plays instantly if what you said matches a cached
  phrase (measured ~2.4s total for text+audio together), otherwise it
  generates live in the background (~30-90s) without blocking the UI —
  you'll see "Generating audio live..." and it plays when ready.

## Latency (measured on this machine, Ryzen 5 3450U)

| Stage | Before | After | What changed |
|---|---|---|---|
| STT | ~9.5s (`small` model) | ~1.7-2.0s (`base` model) | Swapped Whisper model size; benchmarked tiny/base/small, `base` was the best speed/Hindi-accuracy tradeoff available without real Hindi audio to verify `tiny`'s accuracy locally |
| Translation | ~2.3-6.3s (`num_beams=5`) | ~0.7-1.0s (`num_beams=3` + `early_stopping=True`) | Benchmarked beam 5 vs 3 vs 1 on 10 sentences; beam=1 introduced a real repetition defect, beam=3 didn't |
| Total text latency | ~12-19s+ | **~2.4-2.9s** | Both of the above, plus eliminating a one-time ~6s PyTorch warmup tax by running a warmup inference at startup instead of on the first live request |
| Cached audio (text+audio) | same as text (~19s) since audio blocked on text | **~2.4-2.5s** | Same optimizations; cached audio was already non-blocking on text, this just made both paths faster |
| Live (uncached) TTS | ~55-90s | **still ~55-90s (unchanged)** | Confirmed architectural CPU limit, not a tuning gap -- see "Known limitations" |

These numbers are for short (1-3 word) push-to-talk utterances on a warm
server (models preloaded + warmed up at startup, see below). Longer
sentences take proportionally longer for STT and translation.

## Pipeline

```
Mic (browser) --MediaRecorder/WebSocket--> FastAPI backend
   --> Whisper (faster-whisper, CPU)                [Hindi/English -> text]      ~fast
   --> IndicTrans2 distilled (en-indic / indic-indic) [text -> Santali text]     ~fast
   --> text sent to browser immediately
   --> cached phrase? play pre-generated audio : generate live with Indic Parler-TTS   ~slow (30-90s) if live
```

## Model choices & why (read before downloading)

| Stage | Model | Approx. download | Notes |
|---|---|---|---|
| STT | `faster-whisper` "base" | ~140 MB | int8 on CPU, ~1.7-2.0s/utterance (down from "small"'s ~9.5s). "tiny" is faster still (~1.5s) but has a well-documented non-English/Hindi accuracy drop that couldn't be verified locally (no Hindi voice available); "small" gave marginally better accuracy at ~5x the latency. Override with `WHISPER_MODEL`. |
| Translation | `ai4bharat/indictrans2-en-indic-dist-200M` + `...-indic-indic-dist-320M` | ~0.8 GB + ~1.3 GB | **Distilled** variants. Tested the full 1B model too — it's ~10x slower per sentence *and* has the same Santali script-mixing bug (see below), so there's no upside to it here. |
| TTS | `ai4bharat/indic-parler-tts` | ~3.6 GB | The only self-hosted TTS with confirmed Santali support (checked Meta's MMS-TTS and AI4Bharat's own earlier, lighter Indic-TTS — neither supports Santali). Autoregressive, so no fast CPU path exists (see below). |

**Total first-run download: ~6 GB.** All of it is one-time and cached by
HuggingFace afterwards (see `models/README.md`).

**HuggingFace account required.** All three AI4Bharat models are "gated"
(free, instant/auto-approved, but you must be logged in). See Setup below.

## Known limitations (found through testing on this machine)

- **Live TTS is slow: ~30-90 seconds per sentence on CPU**, not "a few
  seconds" as originally hoped. Indic Parler-TTS is a 0.9B-parameter
  autoregressive model (generates audio one codec frame at a time through a
  24-layer decoder) — on this CPU it runs at a fixed ~30x real-time factor.
  We tested full thread count, greedy decoding, and dynamic int8
  quantization — none meaningfully changed it (compute-bound, not a config
  problem). No faster self-hosted Santali TTS model currently exists. This
  is why Demo Mode (pre-cached audio) exists.
- **IndicTrans2 occasionally mixes in the wrong script** (Arabic, Meitei, or
  Odia characters instead of clean Ol Chiki) for certain words — reproduced
  on both the distilled and full 1B models, on greeting words and some verbs
  in particular (e.g. "open"). It's a model quality limitation, not a bug in
  this codebase. The phrasebook phrases were worded/reviewed to avoid known
  triggers; live free-form speech can still occasionally hit this.
- Whisper's language auto-detection is used as-is; very short or noisy audio
  can be misdetected.
- **Phrasebook cache matching is exact-ish (normalized) text matching**, not
  fuzzy/semantic. "Sit down please" won't match the cached "Sit down" entry --
  say phrases close to their listed wording for an instant cache hit.
- On this sandboxed dev machine, the very first Demo Mode load (prefetching
  ~53 audio files as blobs, 5 at a time) can visibly pause the page for a few
  seconds under constrained resources; recovers on its own. Not expected to
  be noticeable on a normal laptop, but worth knowing if it ever reappears.

## Windows-specific fixes already applied in this code (context for future changes)

- `ctranslate2` (faster-whisper's backend) is pinned to `4.4.0` —
  `4.8.2` (the default it would otherwise resolve to) segfaults on load on
  at least some AMD CPUs on Windows (reproduced on a Ryzen 5 3450U).
- `stt.py` sets `KMP_DUPLICATE_LIB_OK=TRUE` before importing `faster_whisper`
  to work around a duplicate-OpenMP-runtime crash.
- VAD filtering is disabled in `stt.py` (`vad_filter=False`) — its
  onnxruntime-based Silero VAD model segfaults independently of the above.
  Not needed for push-to-talk anyway (VAD exists to trim silence from
  continuous audio).
- `translate.py` uses a vendored pure-Python `indic_processor.py` instead of
  the official `IndicTransToolkit` PyPI package, whose Cython build requires
  MSVC Build Tools to compile on Windows. The vendored version is a 1:1 port
  of the same algorithm.
- `torchaudio` is pinned to `2.3.1` to match `torch==2.3.1` — an unpinned
  transitive install resolved to a mismatched version whose native extension
  fails to load.
- Test/build scripts call `sys.stdout.reconfigure(encoding="utf-8")` —
  Windows terminals default to a codepage that can't print Devanagari/Ol
  Chiki text.

Not Windows-specific, but also found during testing: FastAPI's `StaticFiles`
here doesn't answer HTTP Range requests (returns `200` instead of `206` for
a ranged request), which `<audio src="...">` depends on to start loading —
it just stalls forever. `app.js`'s Demo Mode works around this by fetching
phrase audio as a `Blob` and playing that instead of pointing `<audio src>`
directly at the URL. Live Mode was already unaffected (its audio arrives as
base64 over the WebSocket, not a fetched URL).

> Python 3.8, which is end-of-life and too old for current `transformers`/
> `parler-tts` releases. You also have Python 3.11 available (via Anaconda,
> at `C:\ProgramData\anaconda3\python.exe`). Use that explicitly via the `py`
> launcher below — don't use plain `python`.

```powershell

```

## Test each stage individually (recommended before running the full app)

Run these one at a time from the `backend` folder with the venv activated.
Each one downloads only the models it needs.

**Stage 1 — Speech-to-text.** Put a short Hindi or English audio clip in
`test_audio\` (see `test_audio\README.md` for how to record one), then:
```powershell
python scripts\test_stt.py test_audio\sample.wav
```

**Stage 2 — Translation.**
```powershell
python scripts\test_translate.py en "Good morning students"
python scripts\test_translate.py hi "बच्चों, अपनी किताबें निकालो।"
```

**Stage 3 — Text-to-speech.** Use Santali text from the Stage 2 output
(this takes ~30-90 seconds — that's expected, see "Known limitations"):
```powershell
python scripts\test_tts.py "<paste santali text here>" tts_output.wav
```
Play `tts_output.wav` to confirm it sounds right.

## Build the phrasebook (required for Demo Mode)

Generates Santali text + audio for 53 classroom phrases across 6 categories
(greeting, classroom instructions, questions, teaching, encouragement,
ending), once. A first run takes **30-45 minutes** (mostly TTS, ~30-90s per
phrase) — run it during setup, not right before a demo.

```powershell
python scripts\build_phrasebook.py
```

This writes `phrasebook\manifest.json` and `phrasebook\audio\*.wav` (files
named by a slug of their English text, not position). **Idempotent**: if you
add/edit phrases in `scripts\build_phrasebook.py` and re-run it, phrases whose
(English text, translated Santali text) exactly match an existing entry reuse
their audio file instead of paying for TTS again -- only genuinely new/changed
phrases cost the ~30-90s/phrase generation time.

All generated audio (both phrasebook and live) is loudness-normalized after
synthesis: gain is computed to bring the clip's RMS up to -14 dBFS, capped so
the resulting peak never exceeds -1 dBFS (a gain-staged limiter, not
per-sample clipping -- see `_normalize_loudness` in `tts.py`). Raw model
output varied wildly in level (measured peaks from -0.1 to -10.5 dBFS, RMS
from -15.9 to -25.2 dBFS across a handful of clips) -- this makes playback
consistently loud without distorting any of them.

## Run the full app

```powershell
cd "C:\Users\janani vijai\ClaudeProjects\backend"
.\venv\Scripts\Activate.ps1
python -m uvicorn main:app --host 0.0.0.0 --port 8000
```

The first startup preloads all three models (set `$env:PRELOAD_MODELS = "false"`
to skip this and load lazily on first request instead — startup will be
faster but your first translation will be slow).

Open **http://localhost:8000** in your browser.

- **Demo Mode**: click any phrase button — Santali text + audio appear
  instantly, no microphone needed.
- **Live Mode**: allow microphone access, hold the button, speak a Hindi or
  English sentence, release. Santali text appears within a few seconds.
  Audio plays instantly if it matches a cached phrase; otherwise you'll see
  "Generating audio live..." and it plays when ready (~30-90s later).

To test from a phone on the same Wi-Fi, use your laptop's LAN IP instead of
`localhost` (find it with `ipconfig`), e.g. `http://192.168.1.23:8000`.
